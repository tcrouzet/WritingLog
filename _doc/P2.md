# Cahier des charges — Partie 2 : Automatisation et publication en ligne

**Auteur** : Thierry Crouzet
**Destinataire** : Codex (agent de génération de code)
**Date** : 2026-09-09 (révision 2)
**Prérequis** : la Partie 1 (cahier des charges séparé, `CDC_1_dashboard_local.md`) est terminée et fonctionnelle. En particulier :
- un **bootstrap** (`scripts/bootstrap_index.py`) a déjà été exécuté en local avec succès ;
- le dossier `.vault_cache/` qui en résulte est **commité et poussé** dans `tcrouzet/text` ;
- un dossier `site/` autonome et validé existe (dashboard fonctionnel en local).

Ce document ne redéfinit **aucune** règle métier (définitions, classification écriture réelle/import/déplacement, calculs, format des données, contenu du dashboard) : tout cela reste tel que spécifié en Partie 1. Il ne traite que de l'**automatisation strictement incrémentale** et de la **publication**.

---

## 1. Objectif de cette phase

Faire tourner automatiquement, sans intervention manuelle, la mise à jour incrémentale (`scripts/update_index.py`, Partie 1 §5.2) — **jamais le bootstrap complet** —, et publier son résultat (`site/`) sur le web via GitHub Pages, alors que le vault source est un dépôt privé.

## 2. Pourquoi jamais de bootstrap complet en CI

Un run GitHub Actions est plafonné à 6h d'exécution sur runner standard, et un dépôt privé dispose d'un quota gratuit de 2000 minutes/mois. Pour un vault volumineux (années d'historique, un commit ~15 min), un bootstrap complet en CI risquerait de dépasser ce plafond ou d'épuiser le quota en une seule exécution. C'est pour ça que le bootstrap reste une opération **exclusivement locale** (Partie 1, §5.1), sans contrainte de temps ni de quota, et que l'automatisation ne porte que sur l'incrémental — par construction rapide (quelques commits à traiter à chaque run, puisque `.vault_cache/` conserve le curseur du dernier commit traité).

## 3. Dépôts concernés

Deux dépôts GitHub distincts :

- **`tcrouzet/text`** (privé) : contient le vault Obsidian, les scripts Python, `.vault_cache/` (index technique déjà bootstrappé, voir prérequis), et désormais le workflow d'automatisation.
- **`tcrouzet/WritingLog`** (public, [github.com/tcrouzet/WritingLog](https://github.com/tcrouzet/WritingLog)) : dépôt dédié à l'hébergement du dashboard via GitHub Pages. Ne contient jamais de texte brut ni l'index technique, uniquement le code du dashboard et les données déjà agrégées (`site/data/*.json`).

## 4. Principe d'architecture retenu

Le job GitHub Actions tourne dans les Actions du dépôt privé `text` (accès natif à son propre historique Git et à `.vault_cache/` déjà présent, aucune autorisation particulière à demander pour lire le contenu). Il exécute uniquement l'incrémental (`update_index.py`), qui :
1. lit le curseur dans `.vault_cache/` (déjà commité dans `text`, donc disponible directement après le checkout — pas besoin d'aller le chercher ailleurs) ;
2. traite les nouveaux commits depuis ce curseur ;
3. met à jour `.vault_cache/` et `site/data/*.json` ;
4. commite `.vault_cache/` mis à jour dans `text` lui-même (pour que le prochain run reparte du bon curseur) ;
5. pousse uniquement `site/data/*.json` (jamais `.vault_cache/`) vers le dépôt public `WritingLog`.

Cette architecture est plus simple que ce qui avait été envisagé initialement (qui prévoyait d'aller récupérer un état incrémental depuis `WritingLog` avant chaque run) : puisque `.vault_cache/` vit et reste dans `text`, il n'y a plus aucun aller-retour d'état nécessaire entre les deux dépôts. Le flux est strictement à sens unique : `text` → `WritingLog` (uniquement les JSON agrégés).

## 5. Secret nécessaire

Un unique secret à créer, dans **Settings → Secrets and variables → Actions** du dépôt `tcrouzet/text` :

- `WRITINGLOG_PUSH_TOKEN` : un **Personal Access Token fine-grained**, restreint :
  - **Repository access** : uniquement `tcrouzet/WritingLog`.
  - **Permissions** : `Contents: Read and write`.

Ce token n'autorise que l'écriture dans `WritingLog` ; il ne donne à `WritingLog` aucun accès en lecture au contenu de `text`. Le commit de `.vault_cache/` dans `text` lui-même utilise le token par défaut fourni automatiquement par GitHub Actions (`GITHUB_TOKEN`), avec la permission `contents: write` activée dans le workflow — aucun secret supplémentaire à créer pour ça.

## 7. Workflow `.github/workflows/update-dashboard.yml` (dans `tcrouzet/text`)

### 7.1 Déclencheurs

1. Sur chaque `push` vers la branche principale du vault.
2. En complément, un `schedule` cron (ex. toutes les heures), pour couvrir les périodes où la synchronisation Obsidian→GitHub avance en tâche de fond sans déclencher explicitement le workflow au moment voulu.

### 7.2 Étapes

1. Checkout de `text` avec historique complet (`fetch-depth: 0` — nécessaire pour que `update_index.py` puisse retrouver les commits depuis le curseur, même si en pratique il n'en traite que quelques-uns à chaque run).
2. Vérifier que `.vault_cache/` existe (sinon, échouer explicitement avec un message clair : "bootstrap manquant, à lancer en local d'abord" — jamais de fallback automatique vers un bootstrap complet en CI, voir §2).
3. Installer Python + dépendances (`scripts/requirements.txt`).
4. Exécuter `python scripts/update_index.py` (mode incrémental strict, aucune option de rebuild disponible depuis ce contexte).
5. Committer et pousser `.vault_cache/` (index + curseur mis à jour) dans `text` lui-même, uniquement si des changements sont détectés (permission `contents: write` du `GITHUB_TOKEN` par défaut, à activer dans le fichier de workflow).
6. Cloner `tcrouzet/WritingLog` sur le runner, authentifié avec `WRITINGLOG_PUSH_TOKEN`.
7. Copier le contenu de `site/data/` vers `data/` dans le clone de `WritingLog` (ne touche jamais à `index.html`/`style.css`/`dashboard.js`).
8. Committer et pousser vers `WritingLog` uniquement si des changements sont détectés.

### 7.3 Après mise en place

Aucune action manuelle récurrente : GitHub Pages republie automatiquement à chaque nouveau push sur `WritingLog`.

## 8. Mise en place initiale (checklist, une seule fois)

1. En local : exécuter `python scripts/bootstrap_index.py` (Partie 1), committer et pousser `.vault_cache/` dans `text`.
2. Créer le dépôt public `tcrouzet/WritingLog` (vide).
3. Copier dedans le contenu de `site/` obtenu et validé en Partie 1, committer, pousser.
4. Dans `WritingLog` : Settings → Pages → Source = branche principale, racine `/`.
5. Créer le PAT fine-grained (§5), l'ajouter comme secret `WRITINGLOG_PUSH_TOKEN` dans `text`.
6. Ajouter le workflow `update-dashboard.yml` dans `text` (§7), avec la permission `contents: write` activée pour le `GITHUB_TOKEN` par défaut.
7. Vérifier qu'un push dans `text` (ou l'attente du prochain cron) déclenche bien une mise à jour visible sur `https://tcrouzet.github.io/WritingLog/`.

## 10. Points ouverts

- Fréquence exacte du `schedule` cron (toutes les heures proposé par défaut) : à ajuster selon la fraîcheur souhaitée du dashboard vs. consommation de minutes GitHub Actions.
- Que faire si un run échoue en plein milieu (ex. après avoir mis à jour `.vault_cache/` mais avant d'avoir poussé vers `WritingLog`) : le prochain run repartira du curseur déjà avancé dans `.vault_cache/`, donc pas de perte de données côté cache, mais `WritingLog` resterait temporairement désynchronisé jusqu'au run suivant réussi. Comportement jugé acceptable en première version, sans mécanisme de transaction complexe.
- Si le vault continue de grossir sur plusieurs années, envisager à terme un ré-bootstrap complet occasionnel (ex. pour changer la logique de normalisation des empreintes) : toujours en local, jamais en CI, en suivant la même checklist qu'à l'étape 1 de la mise en place initiale (§8).
